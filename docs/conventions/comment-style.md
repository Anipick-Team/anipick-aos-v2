# 주석 컨벤션

주석은 "왜 이렇게 짰는지"를 논문처럼 설명하는 게 아니라, 코드만 보고는 바로 안 잡히는 걸 한두 줄로 짚어주는 용도다. 길게 쓸수록 안 읽는다 — 항상 가장 짧게 쓸 수 있는 문장을 고른다.

## 기본 원칙

- **한 줄, 짧게.** 대상이 뭘 하는지/뭘 나타내는지 명사구나 한 문장으로 끝낸다. 이유·배경·설계 논리를 풀어 쓰지 않는다.
- **자명한 건 안 쓴다.** 타입/이름만 봐도 알 수 있는 파라미터 설명, 뻔한 동작 서술은 생략한다.
- **분기가 있으면 분기 결과만 나열한다.** "왜 이 조건에서 이렇게 처리하는가"를 풀어 쓰지 말고, "조건 → 결과" 형태로 짧게.
- 정 설명이 길어질 것 같으면, 주석을 늘리지 말고 함수/변수 이름을 더 명확하게 바꾸는 걸 먼저 고민한다.

## 1. data/network API 계층

기존 방식 그대로 유지. "어떤 화면/동작에 쓰이는지 - HTTP 메서드 + 경로" 한 줄.

```kotlin
/** 마이페이지 프로필 - GET /users/me/profile */
suspend fun getMyProfile(): Result<Profile, DataError>

/** 리뷰 신고 - POST /reviews/{reviewId}/report */
suspend fun reportReview(reviewId: Long, reason: String): Result<Unit, DataError>
```

## 2. 인터페이스 / 클래스

무엇을 위한 것인지 한 줄. 어떤 모듈이 왜 이 인터페이스에 의존하는지, 구현체가 어디서 오는지 같은 설계 배경은 쓰지 않는다.

```kotlin
// Bad - 배경 설명이 너무 길다
/**
 * 즐겨찾기 상태를 읽고 쓰는 계약. 실제 저장 방식은 이 인터페이스 뒤에 숨겨서
 * ViewModel은 캐시 전략을 몰라도 되게 한다. 구현체는 core:data가 제공하고 Koin이 연결한다.
 */
interface BookmarkStore

// Good
/** 즐겨찾기 상태 읽고 쓰는 인터페이스 */
interface BookmarkStore
```

## 3. 함수

함수가 뭘 확인/처리하는지만 한 줄로. 내부 동작 원리나 "이후 다른 코드가 이걸 어떻게 쓰는지"는 쓰지 않는다.

```kotlin
// Bad
/** 세션이 아직 유효한지 확인한다. 서버 시간 기준으로 만료 여부를 계산하고,
 *  만료 직전이면 백그라운드에서 자동으로 갱신을 트리거하므로 호출부는 신경 쓸 필요 없다. */
suspend fun isSessionValid(): Boolean

// Good
/** 세션 유효 여부 확인 */
suspend fun isSessionValid(): Boolean
```

분기 결과를 설명해야 하면, 조건별로 결과만 짧게 나열한다.

```kotlin
// Bad
/** 시청상태를 변경한다. 이미 "다 봄" 상태면 서버에서 거부하므로 버튼을 막아야 하고,
 *  그 외 상태는 바로 변경 API를 호출하면 된다. */
private fun onWatchStatusClick(status: String) { ... }

// Good
/** 시청상태 변경
 *  이미 "다 봄": 변경 불가, 그 외: 변경 API 호출 */
private fun onWatchStatusClick(status: String) { ... }
```

## 4. 프로퍼티 / Flow

무엇을 나타내는 값인지 명사구 하나. 누가 구독해서 어떻게 쓰는지는 쓰지 않는다.

```kotlin
// Bad
/** 안 읽은 알림 개수를 실시간으로 흘려보낸다. 바텀 네비게이션 뱃지가 이 값을 구독해서
 *  0보다 크면 빨간 점을 표시하는 데 쓴다. */
val unreadCount: Flow<Int>

// Good
/** 안 읽은 알림 개수 실시간 감지 */
val unreadCount: Flow<Int>
```

## 5. 그대로 유지하는 패턴

아래 두 가지는 이미 짧고 표준화돼 있으니 그대로 쓴다.

- `// TODO: <할 일> - <막힌 이유>`
- 네비게이션 전용 액션: `Unit // 네비게이션만 필요한 액션은 Root에서 처리한다.`

## 하지 말 것

- 파라미터 하나하나 뜻 풀이 (`animeId: 애니메이션 기본키` 같은 것 — 이름이 이미 말해준다).
- "왜 이렇게 설계했는지" 서술 (의존성 방향, 다른 모듈/화면과의 관계, 대안과의 비교 등).
- 에러/엣지케이스를 처리하지 않는 이유에 대한 부연 설명. 코드가 그 케이스를 안 다루면 그냥 안 다루는 거고, 굳이 "왜 안 다뤄도 되는지" 주석으로 정당화하지 않는다.
- 이번 작업/이슈 언급 (`// OOO 버그 고치며 추가` 등).
